1. Summary

The robot is a direct-drive (no gearbox) differential platform. An RPi4 runs sensor drivers and odometry; an Arduino Due handles motor PWM and encoder counting; SLAM (Cartographer), RViz2 and planned Nav2 run on a remote PC over WiFi (ROS_DOMAIN_ID=30, ~2–4 ms ping). Major resolved items: encoder serial corruption in firmware, IMU I2C init failure, and RViz LIDAR drops (traced to IMU CPU load). Remaining risks are mainly configuration inconsistencies between files (section 6) and hardware-level items (twitch at boot, cable quality).

4. Odometry & calibration

Wheel circumference = 2π·0.06 = 0.377 m, so one tick = 0.377 / 203 ≈ 1.86 mm (≈ 538 ticks per metre). At the placeholder MAX_WHEEL_SPEED of 0.5 m/s, each wheel produces ≈ 269 ticks/s, or about 13 ticks per 50 ms serial packet.

Linear relation: ticks/s = v × 538. Calibration used 1 manual revolution; 5–10 revolutions divided by N would be more precise.

5. Issues found & status

RViz LIDAR drops: CPU impact of the IMU node

The IMU node used ~35% CPU (much in I/O wait) and starved DDS threads, delaying TF to the remote PC and overflowing RViz's message filter. /scan stayed at a clean 10 Hz, so it was never the bottleneck.

8. Key learnings

  • Single-edge counting is intentional; 203 ticks/rev is not x4 quadrature.
  • A healthy sensor topic rate doesn't rule out a starved DDS thread; profile CPU and D-state.
  • Floating GPIO on an L298N is a real failure mode; use pull-downs.
  • Keep one canonical location per node.

9. Simulation results

Important: these numbers come from a Python kinematic simulation using your real constants (R = 0.06 m, base 0.48 m, 203 ticks/rev, 50 ms packets, midpoint integration as in serial_odom_node.py). They are not measurements from the physical robot. Error magnitudes (e.g. 0.5% tick error) are assumptions. Wheel slip and motor dynamics are not modelled. Script and CSV are provided alongside this report; compare them with real runs.

9.1 Ideal case: quantization only

A 2 m square (4 sides, 4 × 90° turns) with perfect parameters ends with a position error of 0.36 mm and heading error of 0.04°. Single-edge encoding (1.86 mm/tick) is not limiting; parameter error dominates.

9.3 Wheel-base sensitivity

A 1 cm error in the base value produces roughly 7.5° of heading error per full rotation. Since the URDF says 0.50 m and the node 0.48 m, settle this with a measured spin test.

9.4 Calibration method

Assuming ~1% hand-rotation uncertainty, rotating 10 revolutions cuts the tick-count uncertainty about 10× versus the single-revolution calibration currently used.

9.5 Serial faults

Dropped packets barely affect position because ticks are cumulative, but the midpoint integration loses accuracy in turns. Garbled digits (modelled as a dropped leading digit on the left count) cause position jumps of several cm and are not filtered by the current parser; adding a plausibility check (e.g. reject |Δticks| above what max speed allows) is recommended.

12. Runbook

Get the code: git clone https://github.com/SkyFarsa/Farzan.git

Startup

  1. Power the robot; wait for the RPi4 to boot (~45 s).
  2. Check ls -l /dev/turtlebot_arduino and /dev/ttyUSB0 exist.
  3. On the RPi4: ros2 launch my_robot robot.launch.py
  4. On the remote PC, with the same ROS_DOMAIN_ID=30: run Slam.sh, then RViz2.
  5. Verify: ros2 topic hz /scan (≈10), /odom, /imu.
  6. Drive slowly with teleop; reset with ros2 service call /reset_odom std_srvs/srv/Empty.

15. Safety

  • Fit a physical emergency stop that cuts motor power.
  • Firmware watchdog: stop motors if no P command arrives within ~500 ms (not present today).
  • Limit PWM during first floor tests (e.g. ≤ 120).
  • Lift the wheels off the ground when flashing or resetting the Due.
  • Pull-downs on L298N logic and enable pins (PCB phase).
